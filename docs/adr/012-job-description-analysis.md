# ADR-012: Job-description analysis

Status: Accepted, 2026-10-05 (Asia/Kolkata). Implements Phase 2 batch 3 after [ADR-011](011-structured-resume-drafts.md).

- Node resolves existing public catalogue jobs by their 64-hex ID; analysis/history remains private to the authenticated account, including ADMIN. Browser input is only job ID and supported model/reasoning. Python gets trusted owner/context through the service token and no MongoDB/CV/profile credentials.
- Reuse the shared OpenAI Responses adapter and model controls. Generation sends labelled title/company/location/description text only after an explicit Analyze job click. Saved reads do no provider work. Retain current input/output/time bounds and the combined ten-processing-attempts/user/fifteen-minutes allowance. No retries, fallback, automatic ingestion analysis or match scoring.
- A shared `GenerationGate` bounds resume and job generation/review/save together to one active task per intelligence instance, with no queue. Cancellation/shutdown release it. PDF extraction keeps its separate existing worker limit.
- Preserve paragraph text, normalize CRLF/null characters and trim edges. SHA-256 covers canonical normalizer-version/section JSON, excluding import timestamps. This distinguishes content edits from identical refreshes. Both services verify job source hashing.
- Extract typed scalar facts, skills/technologies, experience, education, credentials, languages, eligibility/application requirements, responsibilities, deliverables, benefits and keywords. Unknown scalars stay null; missing arrays stay empty. Known values must be copied from exact section quotes, with word boundaries. Python derives Unicode code-point quote offsets; Node validates them independently. The LLM does not count offsets.
- Determine requirement priority using conservative explicit English qualifiers or recognized preceding headings. Negation/conflicting qualifiers produce unspecified priority; generic headings reset known scope. Every non-unspecified priority has verified source evidence. These rules cannot interpret every natural-language requirement or guarantee semantic correctness; source review remains visible.
- Ambiguity/possible-conflict warnings use bounded, verified quotes and fixed messages. Display listing metadata separately from extracted values and flag differing wording without claiming one is authoritative.
- PostgreSQL migration 002 adds owner/job-bound immutable numbered analyses and deletion tombstones using the existing private database/pool. Same-ID saves are idempotent; fresh successful analysis gets the next number. History has twenty metadata records per page. Default reads prefer the latest analysis of current content, falling back to the latest saved result with a stale flag. Exact-ID reads can show older source versions; stale results are unsuitable for future matching.
- Recheck existence/content in Node after processing. A concurrent edit returns `JOB_CHANGED`; removal returns `JOB_NOT_FOUND`. Expired listings retain readable analyses but block new generation. Ordinary catalogue/profile/auth routes remain usable during intelligence outages.
- Before generation, Node durably tracks owner/job references in `job_analysis_sources`. Every thirty seconds while Node runs, a bounded cursor scan checks source existence. Hard removal hides reads immediately; cleanup deletes that account's derived rows and creates a PostgreSQL tombstone. Downstream failures retain references for retry after restart. Expiry is not removal. No distributed transaction or account-deletion workflow is introduced.

Existing ingestion retains expired listings and has no user hard-delete/reimport flow. Hard-deleted job IDs are treated as retired: their tombstone blocks late writes. A future feature that deliberately reuses such IDs needs an explicit generation epoch/restore design. Cleanup delay can exceed thirty seconds for multiple scan pages or outages.

Saved analysis is informational; it neither changes provider job metadata/search filters nor mutates the user's profile. Matching remains batch 4. Live verification of this new stage requires separate synthetic-call authorization; regular tests mock AI and never load the root OpenAI key into test containers.

Reference: [official OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), checked 2026-10-05.
